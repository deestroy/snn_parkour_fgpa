## The ZedBoard decision, honestly

Using the ZedBoard instead of the planned PYNQ-Z2 has worked, at a cost:

- **No PYNQ/Linux image exists for it**, so the board runs bare-metal C and
  is programmed over JTAG from the Mac with open-source tools. That flow now
  works end-to-end and is scripted, but it took one long night to get there.
- **The board's DDR memory does not work** so far — every controller status
  says healthy but data does not retain. The evidence points at this being
  a 2012-era rev-1.0 Zynq (engineering-sample silicon on a Rev-C board),
  which had known DDR limitations. One test remains (running Xilinx's own
  boot loader, ~10 minutes); if it also fails, DDR is unusable on this board.
- **Consequence if DDR stays dead:** the design runs from the chip's 192 KB
  on-chip memory. This does not block M4–M7 — the network's whole state
  budget was always on-chip by design (that constraint is *stricter* than
  planned, not looser) — but it does mean samples stream one at a time from
  the host, which the UART link forces anyway. The methodology chapter would
  say so plainly.

If a PYNQ-Z2 becomes available later, everything built transfers unchanged;
the ZedBoard would become the secondary/portability board the proposal
already envisaged.

## Confidence

Every hardware module is bit-identical to a Python reference model that is
itself checked against snnTorch — the project's central engineering rule —
and every claim in the table above is backed by a runnable check listed in
the README. The one number that matters most, measured energy per
inference, does not exist yet because the meter does not: that is the
critical path.
